## Границы и договорённости

- Название приложения — «Калькулятор»; скрытый помощник доступен через существующие действия.
- Обычный расчёт независим от ответа ИИ; поиск и импорт не перехватывают экран калькулятора.
- Сохраняются черновики, решения, место чтения, тихая готовность и существующее фоновое выполнение.
- Примеры нужны агенту для решения; ручной просмотр библиотеки служит управлению материалами.
- Проверенность загруженного решения не предполагается автоматически. Ответы ИИ из истории
  должны сохранять своё происхождение и отдельный статус проверки.
- Предлагается локальное хранение библиотеки; выбранные материалы передаются используемому API.
  Распознавание и embeddings могут требовать внешнего сервиса — этот выбор ещё не сделан.
- API-ключ не включается в файлы задач, индекс, экспорт, журнал инструментов и диагностические данные.
- Публикация релизов только из отправленной ветки `main`; подпись остаётся локальной.

## Предлагаемая последовательность

1. Выполнить ограниченную [декомпозицию ViewModel и сборки зависимостей](#viewmodel-decomposition) и [упростить документацию](#documentation-maintenance), сохраняя поведение и след проверок.
2. Измерить [качество и скорость текущего поиска](#retrieval-quality) на размеченном наборе и библиотеке до 500 задач. По результатам исправлять ранжирование, без добавления embeddings наугад.
3. Завершить [приёмку инструментов агента](#agent-tools) и [импорта](#library-import): API 26, прерывание процесса, фон, отмена и сложные документы. Проверки экспериментального Koog не считать проверками текущего транспорта.
4. Доработать [возврат в библиотеку и фильтры](#library-ui), [поиск по истории](#history-search), затем переход от прочитанного примера к оригиналу в [источниках ответа](#solution-sources).

Последовательность выше относится к работе после стабилизации калькулятора; реализация поисковых улучшений ещё не начата.

Ручной поиск по истории уже входит в общий поиск; сохранение запроса при возврате ещё предстоит.
Отмена удаления, подготовка фото и резервные копии остаются отдельными кандидатами.
MCP отложен до потребности использовать библиотеку из других приложений.

## Стабилизация режимов калькулятора

Type: `Issue`
Status: `done`
Priority: `high`
Source: `user-ops`
Safety impact: `low`

Объём: вынести выбор режима дисплея, переходы редактора и черновиков, доступность действий,
код ✦, обработку клавиатуры и подготовку сохраняемого сеанса в тестируемую модель Kotlin.
`AssistantDisplay` сохраняет владение видимостью/непрочитанностью ответа; запросы и навигация
остаются у прежних владельцев. Compose-адаптер выполняет команды модели и передаёт события.
Разделение всего `SolutionViewModel`, смена транспорта, исправления импорта и новые функции не входят.
По отдельному уточнению пользователя исправлена арифметика процентов в `ExpressionParser`;
предпросмотр и «=» используют один парсер, числовое дополнение остаётся вопросом к ИИ.
Уточнение от 2026-10-16 привязывает ввод к видимому режиму: обычный калькулятор не открывает
редактор, даже если решение сохранено и скрыто. Ввод доступен в режиме ИИ и при показанном ответе.

### Критерии приёмки

- [x] Переходы и выбор режима вынесены из `CalculatorScreen` в `CalculatorModes`; модель не зависит от Compose, ViewModel и Android lifecycle.
- [x] Тесты охватывают расчёт, редактор задачи/дополнения, черновики, повтор после ошибки, ✦, свайп, код, клавиатуру, смену решения и тихое завершение.
- [x] Сохранены «C» на ответе, числовое дополнение, удержание цифр/«=» и подготовка запроса библиотеки.
- [x] В обычном калькуляторе ввод отключён, в том числе со скрытым решением; меню ИИ и показанный ответ сохраняют ввод.
- [x] Проценты проверены для +/−, отдельных значений, ×/÷, скобок, знаков, последовательных поправок и сокращения процентных множителей.
- [x] Полный JVM-набор, lint, сборка и проверки Compose-адаптера на изолированном Android-пакете завершены.
- [x] Визуальный обход через «Компьютер» выполнен с фокусом только на окне эмулятора.
- [x] Зафиксированы проверенные границы восстановления и оставшиеся ограничения приёмки.

Уточнение ввода от 2026-10-16 проверено отдельно: **396 JVM-тестов, 0 падений/ошибок/пропусков**,
в том числе 32 теста режимов, и **6 Android-тестов на API 35**. Проверены восстановленный сеанс
со скрытым решением, скрытие через «C», возврат удержанием ✦, дополнение на показанном ответе
и ввод в меню ИИ. Тестовый пакет удалён; при этих проверках пользовательская 1.6.2 не заменялась.
Затем локальная подписанная сборка 1.6.3 установлена поверх 1.6.2 с сохранением данных:
сборка и `lintRelease` завершились успешно, сертификат совпадает с исходным. В окне эмулятора
проверены отсутствие ввода по тапу в обычном калькуляторе после запуска и закрытия редактора,
а также доступность ввода в режиме ИИ. На эмуляторе остался один пакет калькулятора.
Эти проверки относятся к исправлению для версии 1.6.3.

Проверки при выпуске 1.6.2: **394 JVM-теста, 0 падений/ошибок/пропусков**, в том числе 30 тестов
режимов и 14 тестов парсера; `lintDebug` — 0 ошибок, 26 предупреждений; сборки приложения и тестового APK успешны.
На API 35 прошли **6 Android-тестов** в `com.smartcalc.app.importcheck`: пересоздание Activity с
арифметическим редактором и дополнением, сохранение черновика/возврат к ответу, «C»/удержание ✦,
предпросмотр и результат `20−2%`, отсутствие ввода в чистом калькуляторе и сохранение ввода
после получения результата ИИ. Сетевые запросы не запускались, основной пакет не заменялся.
В первом полном прогоне старый тест импорта не уложился в 3 секунды при параллельной нагрузке;
отдельный повтор и последующие полные прогоны прошли без изменения кода импорта.

Через «Компьютер» выбран только `Android Emulator - SmartCalc_API35:5554`; все вводы и снимки
выполнены через привязанный к этому окну `sky`. ADB использовался для подготовки: запуска
изолированного APK и копирования синтетического Markdown, без управления интерфейсом и снимков.
Проверены `20−2%` → предпросмотр/результат `19.6`, редактирование расчёта и сохранение после
закрытия клавиатуры, меню помощника, локальный импорт тестовой задачи и перенос на калькулятор,
повторное открытие черновика дополнения, снятие привязки к ответу и отдельный черновик новой задачи,
возврат к прежнему расчёту через «C» и к сохранённому ответу свайпом вверх. Запросы к модели не отправлялись.
После уточнения пользователя через то же окно повторно проверены запрет ввода в чистом
калькуляторе, команда «Написать» и доступность ввода после «На калькулятор» → «C» при полученном
синтетическом результате. Эмулятор оставлен открытым на обычном дисплее; управление «Компьютером» освобождено.

Границы исходной итерации: пересоздание Activity подтверждено Android-тестами, восстановление после нового
процесса — JVM-тестами подготовки/чтения сеанса. Отдельный force-stop на устройстве и API 26
не проверялись. Тёмная тема и шрифт 200% проверены позднее отдельным
[прогоном 2026-10-16](ui-layout-check-2026-10-15.md#theme-font-check-2026-10-16), с указанными там ограничениями.
Удержание ✦ проверено
Android-тестом, скрытие кодом и ограничения доступности жеста — JVM-тестами. Это не закрывает
отдельную приёмку фоновых сетевых запросов и импорта ниже.

Замечание о путях macOS: в `HistoryStoreTest` родительские каталоги сравниваются через
`canonicalFile`, чтобы учитывать `/var` → `/private/var`. Отдельного прогона на Mac не было;
прохождение тестов Windows не считается подтверждением проверки macOS.

## Декомпозиция SolutionViewModel и сборки зависимостей

Type: `Issue`
Status: `open`
Priority: `high`
Source: `user-ops`
Safety impact: `medium`

### Краткое описание и цель

По замечанию Клода `SolutionViewModel` одновременно обслуживает текущее решение, чтение,
библиотеку, шаблоны, настройки и проверку подключения. В `SmartCalcApplication` вручную
связаны хранилища, импорт и фоновые сервисы. Выделить владельцев этих обязанностей так,
чтобы изменение библиотеки не требовало изменения состояния текущего решения.

### Объём задачи

Входит: описать текущих владельцев состояния и время жизни; отделить операции библиотеки/шаблонов
и состояние чтения от координации текущего решения; сделать создание библиотечного импорта
явным отдельным узлом сборки зависимостей. Использовать существующие `LibraryImportViewModel`,
`GenerationController` и `SessionStore`, переносить обязанности небольшими проверяемыми шагами.

Не входит: новые функции, изменение формата данных или транспорта, внедрение DI-фреймворка,
переписывание `CalculatorModes` и автоматические сетевые запросы при запуске.

### Затронутые области

`SolutionViewModel.kt`, `SmartCalcApplication.kt`, `ui/library/LibraryImportViewModel.kt`,
`ui/AppRoot.kt`, `data/session/`, `data/request/`, `data/library/importer/` и затронутые UI-потребители.

### Критерии приёмки

- [ ] Зафиксированы владельцы текущего решения, сеанса чтения, библиотеки/шаблонов и фоновых операций; у каждого состояния один писатель.
- [ ] Операции библиотеки/шаблонов и сохранение чтения имеют отдельные тестируемые границы; `SolutionViewModel` не содержит их реализации.
- [ ] Создание импорта вынесено из большого выражения в `SmartCalcApplication`; время жизни контроллеров и фоновых scope явно задано, повторная композиция не создаёт второй экземпляр.
- [ ] Сохраняются расчёт, скрытие/возврат ответа, черновики, дополнения, место чтения, фоновый запрос, отмена и ручной повтор без дублирующих платных запросов.
- [ ] Полный JVM-набор, сборка и целевые Android-проверки переходов/восстановления проходят; изменения разбиты на проверяемые шаги без миграции пользовательских данных.

темах, другой вопрос при том же условии, многостраничные решения, плохие фото, таблицы,
формулы Word, отсутствие аналога и ошибочные авторские решения. Фиксировать ожидаемые
источники и существенные ошибки распознавания; оценивать качество поиска отдельно от ответа модели.

Не входит: утверждение качества по одному удачному примеру и включение пользовательских файлов в Git без разрешения.

### Затронутые области

Новые обезличенные фикстуры и проверки в `app/src/test/`, ручные сценарии импорта и поиска.

### Критерии приёмки

- [ ] Набор охватывает все перечисленные классы случаев и каждый выбранный формат импорта.
- [ ] Для поисковых запросов размечены ожидаемые подходящие и заведомо неподходящие примеры.
- [ ] Критерии и пороги качества согласованы до сравнения реализаций; записаны результаты и известные ограничения.
- [ ] Платные/сетевые проверки запускаются отдельно; ключи, частные материалы и реальные ответы не попадают в обычные тестовые логи.

## Поиск по истории собственных решений

Type: `Issue`
Status: `partial`
Priority: `medium`
Source: `conversation`
Safety impact: `low`

**Перенесённые наработки (2026-10-12):** Есть: общий экран поиска индексирует исходный вопрос, ответ, шаги и дополнения истории, включая открытые библиотечные задачи, без дублирования. Результат открывает существующее решение. Просмотр результата через TaskPreviewScreen сохраняет запрос внутри SearchScreen. Осталось: сохранять его после действия «На калькулятор» и повторного входа через меню; этот переход закрывает маршрут поиска.

### Краткое описание и цель

Вручную находить сохранённые ответы через общий поиск. Основная часть перенесена из task-search;
это не заменяет согласованный поиск для агента.

### Объём задачи

Входит: поиск по условию, ответу и дополнениям, открытие найденной записи с сохранением текста запроса.
Не входит: автоматическое признание истории проверенной библиотекой и RAG.

### Затронутые области

`ui/search/SearchScreen.kt`, `data/search/TaskSearch.kt`, `data/history/HistoryStore.kt`.

### Критерии приёмки

- [x] Находится запись по исходному вопросу, ответу и дополнению; пустая выдача понятна.
- [ ] Строка запроса сохраняется при открытии результата и повторном входе в поиск.
- [ ] Очистка строки восстанавливает список; открытие результата не меняет само решение.
