# Импорт документов в библиотеку: схема следующего этапа

Дата: 2026-10-12. Основание: интегрированная `main` / `4dc4363`.
Статус: подготовлено для проверки пользователем; продуктовый код этого этапа ещё не написан.

Пользователь уточнил последовательность: интеграция `codex/library-metadata`, затем импорт
PDF/Word/фотографий с разделением на задачи, сохранением оригиналов и ссылок на страницы;
после этого автоматический поиск примеров агентом. Этот документ конкретизирует второй этап.
Общая цель и дальнейший RAG описаны в [архитектуре](2026-10-12-library-rag-design.md).

## 1. Результат для пользователя

В «Базе задач» пользователь выбирает PDF, DOCX, фотографии, TXT или Markdown. Приложение
сохраняет копию оригинала, показывает выбранные страницы/фрагменты и способ обработки,
получает отдельные черновики задач с условием, авторским решением и ответом. Перед добавлением
можно исправить текст, объединить продолжение, разделить несколько задач и исключить лишние.
Из каждого примера можно открыть соответствующую страницу или фрагмент сохранённого оригинала.

Подтверждение разбора не означает математической проверки. Новые примеры получают
«Не проверено»; спорные знаки, формулы или границы требуют отдельного разрешения замечания
перед включением в поиск. Ошибки автора сохраняются как часть исходного материала.

Импорт работает независимо от текущего решения и калькулятора. Закрытие экрана сохраняет
черновики, а завершение не переключает пользователя в библиотеку автоматически.
Автоматическое использование примеров при решении — следующий этап, после приёмки импорта.

## 2. Варианты и выбранное предложение

| Вариант | Что даёт | Цена и ограничение |
|---|---|---|
| A. Расширить существующие JSON-хранилища, добавить журнал и распознавание через настроенный API | Сохраняет реализованные версии и редактор; можно проверять этапы отдельно | Нужен восстанавливаемый протокол публикации между журналом и библиотекой |
| B. Перенести библиотеку в Room до импорта | Общие транзакции для задач, источников и журнала | Дополнительная миграция всей базы и зависимостей до появления нового пользовательского сценария |
| C. Вынести импорт на отдельный сервер | Тяжёлая обработка вне телефона | Новый сервис, авторизация, хранение документов вне устройства |

Предложение: A для данного этапа. `TemplateStore` остаётся хранилищем опубликованных задач;
оригиналы и незавершённые импорты имеют отдельный репозиторий. Переход на Room не нужен для
этого результата. Он остаётся возможным при дальнейших измерениях и развитии поиска.

## 3. Источники, версии и ссылки

- `LibrarySource`: UUID, отображаемое имя, подтверждённый формат, размер, SHA256,
  относительный внутренний путь к оригиналу, число страниц/блоков, признак включения.
  Имя файла и внешнее URI не служат постоянным идентификатором.
- `SourceSegment`: ID источника и номер страницы PDF либо ID/порядок блока DOCX/TXT;
  для фотографии — ID изображения. При наличии сохраняется прямоугольник области.
  Нумерация PDF в UI начинается с 1. В DOCX не выдумываются стабильные номера страниц.
- `ImportDraft`: локальный UUID, условие, решение, отдельный ответ, изображения,
  ссылки на сегменты, замечания распознавания, отметка исключения и ревизия черновика.
- Текущая `LibraryMetadata` и каждая `LibraryRevision` получают необязательные ссылки на
  сегменты и происхождение импорта. Старые JSON без этих полей остаются читаемыми;
  версии сохраняют собственные ссылки вместе с текстом и фотографиями.
- Повтор SHA256 показывает существующий источник и обработанные диапазоны. Новый диапазон
  добавляется к нему. Повторный разбор создаёт сравниваемый черновик; локальные правки
  опубликованного примера не заменяются автоматически.

Оригинал копируется потоково во временный файл, проверяется и только затем публикуется
атомарным переименованием. Неудачная копия не создаёт видимый источник. Потерянное разрешение
на URI после этого не влияет на сохранённый импорт. Все внутренние пути создаёт приложение.

Удаление исходника требует явного действия: примеры с его ссылками выключаются для нового
поиска, текст и собственные изображения примеров сохраняются. Старые решения истории
продолжают открываться; вместо оригинала показывается отметка удаления. Экспорт существующих
ZIP/JSON/Markdown по-прежнему переносит самостоятельный текст и фото, а не чужие локальные пути.

## 4. Извлечение и распознавание

Новый `DocumentExtractor` не использует ограничения `DocumentReader` для одной задачи.
Текущая отправка документов на решение продолжает использовать свой существующий путь.

| Формат | Локальная подготовка | Привязка и ограничения |
|---|---|---|
| PDF | Последовательный рендер выбранных страниц; на API 35+ доступный текстовый слой используется дополнительно | Оригинал и номер страницы сохраняются; на API 26–34 основа распознавания — растр |
| DOCX | Разбор XML абзацев, таблиц, рисунков и OMML с ограничениями распаковки | Ссылки на блоки; неподдержанная формула/рисунок оставляет видимое замечание |
| JPEG/PNG и снимок камеры | Копия исходных байтов; подготовка с учётом EXIF без изменения оригинала | Ссылка на изображение и область; несколько фото имеют явно заданный порядок |
| TXT/Markdown | UTF-8, при ошибке декодирования Windows-1251; сохранение структуры блоков | Структурированные задачи разбираются локально; произвольный сборник требует разделения |
| Старый DOC | Отказ до распознавания с предложением сохранить DOCX/PDF | Прежняя библиотека и черновик не изменяются |

[`PdfRenderer.Page.getTextContents`](https://developer.android.com/reference/android/graphics/pdf/PdfRenderer.Page#getTextContents())
добавлен на API 35: это нельзя делать обязательным условием для приложения с minSdk 26.
Наличие текстового слоя не доказывает полноту формул; изображение страницы остаётся доступным.

`DocumentRecognizer` получает только выбранные сегменты и возвращает проверяемый JSON:
черновики, ссылки на переданные ID сегментов, замечания и незаконченное продолжение задачи.
Ответ с неизвестным сегментом, чрезмерным объёмом или неверным JSON не публикуется.
Текст документа передаётся как материал для извлечения, а не как инструкция инструментам.
Распознавание не решает задачи заново и не исправляет авторскую арифметику.

Используется профиль API пользователя. Поддержка изображений задаётся явно в настройках,
а не выводится из имени модели. При отсутствии этой возможности оригинал и локальные данные
сохраняются; доступны ручной ввод и смена профиля. Фотографии не отправляются текстовой модели.
Перед сетевой обработкой видно, какой материал будет отправлен, диапазон и предел запросов.
Цена показывается только при известных тарифе и usage; иначе — объём и число запросов.

## 5. Лимиты первой реализации

Значения из общего предложения становятся проверяемыми контрактами этого этапа:

- 100 МиБ на исходный файл; до 100 выбранных страниц за один импорт.
- 8 МиБ XML на часть DOCX, 64 МиБ суммарно распакованных данных, 2 МиБ текста на единицу
  локального чтения; контроль ведётся по фактически прочитанным байтам.
- До 4 мегапикселей на декодированную растровую страницу; страницы не держатся все в памяти.
- Сетевой пакет: до 2 растровых страниц или 12 000 Unicode-символов текста. Переносимое
  продолжение задачи входит в этот бюджет. Ограничение символов не выдаётся за токены.
- До 10 внешних POST на одно явное действие «Обработать»/«Продолжить», включая fallback
  без `response_format`. Тайм-аут одного POST — 120 секунд, активного запуска — 8 минут.
- До 500 опубликованных задач в библиотеке этого сценария. При превышении пользователь
  выбирает меньший набор; сохранённый разбор остаётся доступным.

Большой документ не обрезается молча: показываются полный объём, выбранный диапазон,
обработанная часть и остаток. Длинное продолжение остаётся черновиком с замечанием.
Ошибка нехватки диска сохраняет предыдущее состояние; временные файлы убираются после отката.

## 6. Журнал, фон и публикация

`LibraryImportController` имеет собственный журнал и службу; он не занимает слот
`GenerationController` и не меняет его решение/черновик. Один импорт обрабатывается за раз;
другие источники можно сохранить в ожидающем состоянии. Между пакетами импорт уступает
сеть и декодирование интерактивному решению. Активный импорт имеет тихое уведомление
«Обрабатывается документ» без текста материала; пауза и ожидание проверки не держат службу.
Остановка Android сохраняется как прерывание, без обещания вечной фоновой работы.
Учитываются [ограничения служб Android](https://developer.android.com/develop/background-work/services/fgs/timeout).

Стадии: `copied → extracting → recognizing → review_required → publishing → ready`;
отдельные состояния `paused / failed / interrupted / cancelled`.
Каждый локальный сегмент и ответ распознавания сохраняются до следующего шага.
Перед POST записываются номер попытки, ID сегментов и бюджет, без ключей и заголовков.
После остановки процесса неизвестный исход POST требует ручного повтора. Уже записанный
ответ обрабатывается локально. Поздний ответ отменённой попытки не меняет новый импорт.

Публикация выбранных черновиков — восстанавливаемая операция:

1. Журнал атомарно сохраняет намерение, детерминированные ID задач, ревизии черновиков,
   снимок целевого раздела и подготовленные собственные изображения.
2. `TemplateStore` сохраняет весь выбранный набор одним атомарным обновлением,
   проверяя ожидаемую версию раздела. Видимое состояние публикуется после записи.
3. Журнал отмечает подтверждённые ID. После остановки между шагами 2 и 3 контроллер
   сверяет ID и снимки в библиотеке и завершает отметку, не добавляя задачи повторно.

Конфликт редактора или неподтверждённый частичный результат блокирует публикацию и сохраняет
черновики. Ссылки на оригинал допустимы только после сохранения самого источника.
Подтверждённые задачи не удаляются очисткой временных файлов незавершённого импорта.

## 7. Интерфейс и границы файлов

Вход остаётся ✦ → 9 → «База задач». Внутри — «Задачи» и «Файлы»; существующие разделы,
редактор, версии и импорт готовых ZIP/JSON сохраняются. Во «Файлах» видны источники,
диапазоны, прогресс, ошибки и действия «Продолжить», «Проверить разбор», «Открыть оригинал».
Системный выбор файлов и камера сохраняют ожидающее действие при пересоздании Activity.

Экран проверки показывает карточки задач, поля условия/решения/ответа, замечания и ссылку
на соответствующие сегменты. Объединение и разделение явно сохраняют распределение ссылок;
неустановленные границы помечаются до добавления. «Добавить выбранные» возвращает библиотеку,
а «Назад» сохраняет разбор. Экран оригинала PDF открывает указанную страницу внутри приложения;
DOCX показывает сохранённые блоки с возможностью открыть исходный файл.
Внешнее открытие использует временный `content://` доступ только к выбранному файлу через
[FileProvider](https://developer.android.com/training/secure-file-sharing/setup-sharing).

Ответственности:

- `data/library/source/`: модели источников/сегментов, копирование, SHA256, доступ к оригиналу.
- `data/library/import/`: модели черновиков, журнал, лимиты, публикация и контроллер.
- `data/library/extract/`: отдельные адаптеры PDF, DOCX и текста; подготовка изображения.
- `data/api/DocumentRecognizer`: сборка запроса и разбор ответа; транспорт с учётом бюджета.
- `ui/library/`: источники, выбор диапазона, проверка черновиков, просмотр оригинала.
- Точки интеграции: `LibraryMetadata`, `TemplateStore`, `SmartCalcApplication`, `SolutionViewModel`,
  `AppRoot`, `LibraryScreen`, настройки возможностей API, manifest и конфигурация FileProvider.

Посторонний рефакторинг калькулятора, переход на Responses API, embeddings и цикл инструментов
модели не нужны для приёмки импорта.

## 8. Проверки и порядок выполнения после согласования

Каждый пакет имеет самостоятельную проверку и отдельный коммит:

1. Синтетические файловые фикстуры I01–I14, источник и ссылки версий; повтор по SHA256,
   ошибка копирования, потеря URI, перезапуск и сохранность старой библиотеки.
2. Локальное извлечение PDF/DOCX/текста: более 4 страниц, две задачи на странице,
   продолжение на следующей, таблицы, OMML, EXIF, лимиты, повреждённый/защищённый файл.
3. Распознавание и журнал на поддельном транспорте: пакет/перенос, неправильные ссылки,
   нечитаемый знак, инъекция инструкции, бюджет fallback, отмена и неизвестный исход POST.
4. Проверка/публикация и UI: объединение, разделение, исключение, сбой записи, остановка
   между публикацией и отметкой журнала, повтор без дублей, открытие каждой ссылки.
5. Полные JVM-тесты, lint, APK и проверка на эмуляторе без очистки данных. Отдельно проверить
   минимальный API 26 и API 35, независимость текущего решения и фоновые ограничения.

Пользовательский «Вариант 3.jpg» не является тестовой фикстурой. API-ключи не читаются
при разработке и не записываются в Git/журнал/логи; реальные платные проверки остаются
отдельным явно запущенным действием. Результаты I01–I14 записываются с ограничениями,
а наличие фикстуры само по себе не считается успешным импортом.

После утверждения этой схемы создаётся детальный план реализации. После приёмки импорта —
отдельный план автоматического поиска примеров, бюджета контекста и источников в ответах.
