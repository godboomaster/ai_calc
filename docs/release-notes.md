# Как готовить описание релиза

Эти правила применяются к агентам и разработчикам, выпускающим «Калькулятор». Технические команды находятся в [процессе выпуска](releases.md).

## Сначала установить состав изменений

1. Получите актуальные ветки и теги. Найдите предыдущий опубликованный стабильный релиз через GitHub Releases; не угадывайте его по локальной ветке или номеру версии.
2. Просмотрите его описание для сохранения языка и стиля. Сравните предыдущий тег с выпускаемым коммитом: `git log PREVIOUS..HEAD` и `git diff PREVIOUS..HEAD`.
3. Проверьте фактическое поведение по коду и результатам проверок. Название коммита, план или бэклог сами по себе не доказывают готовность функции.
4. Включайте только попавшие в выпускаемый коммит изменения. Не перечисляйте планы, отдельные экспериментальные ветки и функции прошлых версий как новые.

## Что и как перечислять

- Пишите по-русски. Заголовок релиза: `Калькулятор X.Y.Z`.
- Начните с короткой фразы о главном результате. Далее сгруппируйте изменения в 2–4 понятных раздела по пользовательским сценариям либо «Новое», «Улучшения», «Исправления». Пустые разделы не нужны.
- **Новое** — ранее недоступная возможность. **Улучшение** — изменение существующего сценария. **Исправление** — устранение конкретного неправильного поведения. Не называйте исправление новой функцией.
- Один пункт — одно связное изменение: где оно заметно и что теперь происходит. Например: «Кнопка сохранения подключения остаётся доступной над системной клавиатурой».
- Для бага опишите симптом и результат: «Клавиши калькулятора больше не растягиваются при прокрутке, когда все кнопки помещаются на экране».
- Укажите существенные условия и границы: в этом примере прокрутка остаётся на очень низком экране. Не обещайте «все экраны», «любые модели» или «полную безопасность», если это не подтверждено.
- Объединяйте связанные коммиты в один пользовательский пункт. Не копируйте технические сообщения, хеши, пути файлов, названия классов и историю промежуточных попыток.
- Чистый рефакторинг, тестовые фикстуры и документацию обычно не включайте в основной список. Если это важно для разработчиков, добавьте короткий отдельный раздел.
- Проверки упоминайте только выполненные на соответствующих исходниках, с точным охватом. Сборка не заменяет визуальную проверку. Не переносите число тестов из прошлого релиза без проверки.

## Установка и совместимость

Всегда добавляйте блок установки: какой APK скачать и можно ли установить его поверх прошлой версии. Утверждайте сохранность настроек и данных при обычном обновлении только при сохранённых package ID и сертификате. Не советуйте удалить приложение перед совместимым обновлением.

Указывайте `Calculator.apk.sha256` как файл контрольной суммы и добавляйте ссылку сравнения предыдущего и нового тегов. Если есть несовместимость или обязательные действия пользователя, сообщите о них явно перед инструкцией установки.

## Шаблон

```markdown
Коротко: главное изменение этой версии.

## Улучшения

- Конкретное изменение и его польза для пользователя.

## Исправления

- Где возникала проблема и что теперь работает правильно.

## Установка

Скачайте **Calculator.apk** и установите поверх прежней версии «Калькулятора».
Пакет и сертификат подписи сохранены; удалять приложение не нужно.
При обычном обновлении сохраняются ключи, настройки, история решений и библиотека.
Файл **Calculator.apk.sha256** содержит контрольную сумму.

[Все изменения с версии PREVIOUS](https://github.com/godboomaster/ai_calc/compare/vPREVIOUS...vVERSION)
```

Это структура, а не готовые факты: блок совместимости и каждый пункт нужно проверить для текущего выпуска.

## Публикация и последняя проверка

Подготовьте UTF-8 Markdown-файл с настоящими переносами строк до запуска выпуска. Не передавайте многострочный текст через собранные вручную shell-аргументы.

Текущий `scripts/release.py` создаёт автоматические notes. После его успешного выполнения замените их подготовленным описанием через `gh release edit TAG --repo godboomaster/ai_calc --title "Калькулятор VERSION" --notes-file PATH`. Сохраните служебную строку `<!-- smartcalc-local-release: FULL_COMMIT_SHA -->` в начале текста. Не оставляйте автоматические notes конечным результатом.

Проверьте через `gh release view`: название и тело опубликованы полностью, версия соответствует APK, релиз не остался черновиком, оба файла доступны. В ответе пользователю дайте ссылку на релиз и кратко назовите главное.
